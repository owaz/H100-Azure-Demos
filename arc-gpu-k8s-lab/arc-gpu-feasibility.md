# Feasibility: H100 Spot VM for Arc-Kubernetes / GPU experimentation

**Date:** 2026-10-20 (revised)
**Scope:** Can the existing `h100-spot-llm-lab` Azure H100 Spot VM be repurposed to experiment with (a) plain Azure Arc-enabled Kubernetes running NVIDIA GPU workloads, versus (b) the **AKS enabled by Azure Arc** product family? Started from the Azure Arc Jumpstart `azure_arc_k8s` scenarios and verified every load-bearing claim against current Microsoft Learn, K3s, and NVIDIA primary docs.

**Implementation decision:** This assessment is background research, not authorization to repurpose the existing VM. The [lab deployment](README.md) creates a **new**, isolated H100 Spot VM and uses NVIDIA GPU Operator rather than the manual device-plugin route discussed below. The existing Spot VM lab remains reference-only.

## TL;DR

- **"AKS enabled by Azure Arc" is a family of distinct, separately-hosted products, none of which this Spot VM can be.** Per Microsoft's own platform-comparison page, "AKS Hybrid and Edge" spans four infrastructure targets: **AKS (Azure, cloud)**, **AKS on Azure Local** (version 23H2+, managed via a lightweight appliance automatically deployed with Azure Local), **AKS Edge Essentials** (PC-class Windows 10/11 or Windows Server hosts, self-managed, one Hyper-V-isolated VM per node), and **AKS on Windows Server** (a separate legacy offering managed via a PowerShell-installed "management cluster"). A standalone Azure IaaS VM is none of these targets.
- The specific product that provides GPU node pools today is **AKS on Azure Local**, and Microsoft's own GPU support matrix for it lists only **NVIDIA A2, A16, T4, L4, L40, L40S, and RTX Pro 6000** on specific `NCx_*`/`NKx` Azure Local VM sizes — **H100 is not on that list**. So even setting aside "can't host AKS-Arc on a standalone Azure VM," an H100-based AKS-on-Azure-Local GPU experiment isn't a supported hardware combination today.
- **Azure Arc-enabled Kubernetes** (the generic `az connectedk8s connect` cluster-attach service) is architecturally different from the AKS products above: it connects CNCF-certified Kubernetes clusters to Azure management. Standing up K3s or kubeadm on the existing Spot VM and connecting it with `connectedk8s` is a **technically viable experiment**, not a deployment validated by this assessment. K3s appears in the [Arc validation program](https://learn.microsoft.com/azure/azure-arc/kubernetes/validation-program); that does not establish certification of this exact H100/Ubuntu/driver/runtime combination or make Microsoft responsible for the self-managed cluster's lifecycle.
- Running GPU workloads under k3s requires the **NVIDIA Container Runtime** to be present so K3s's embedded containerd auto-detects it and generates a `RuntimeClass`; pods must then explicitly set `runtimeClassName: nvidia` (or you change the node default). This is a different, more specific step than a bare `nvidia-ctk runtime configure --runtime=containerd` call — see Caveats.
- Azure Spot eviction and single-node topology are compatible with Arc cluster-connect (outbound-only), but the experiment should be understood as a connectivity/scheduling proof-of-concept, not a representative test of any Microsoft-supported AKS-Arc product.
- Nested virtualization / GPU passthrough questions (e.g., running Azure Local or AKS Edge Essentials *inside* the Spot VM to approximate "real" AKS-Arc) **could not be confirmed as supported** on the H100 NC-series sizes used here, and are **not recommended**.

## Recommended experiment

Run the **Azure Arc-enabled Kubernetes** scenario on the existing Spot VM as a self-managed lab (not a stand-in for AKS on Azure Local). These are proposed steps, not a deployment performed or verified on a live VM:

1. Keep the current Docker Compose vLLM/LiteLLM stack as the primary workload. Before running a GPU-scheduled test pod under k3s, **stop whatever is currently holding the GPU(s)** in Compose (`docker compose down` or similar) so there's no contention — compatible installs (Docker + k3s/containerd side by side) can otherwise coexist on the host; it's concurrent GPU *use* that conflicts, not the installations themselves.
2. Install **k3s** (simplest single-node option; the Jumpstart repo documents "Rancher K3s" as one of its supported self-managed-cluster connect scenarios) — it ships with an embedded containerd by default.
3. The driver already installed by [`bootstrap-host.sh`](../h100-spot-llm-lab/scripts/bootstrap-host.sh) is the NVIDIA datacenter driver; additionally install the **NVIDIA Container Toolkit packages** per the official K3s guidance (`nvidia-container-toolkit` / `nvidia-container-runtime`, from the `nvidia.github.io/libnvidia-container` repo already added by the bootstrap script). K3s's embedded containerd **auto-detects** the NVIDIA Container Runtime on `PATH` at startup and writes it into its own generated `containerd` config, producing a Kubernetes `RuntimeClass` named `nvidia` for you — you do not need to (and should not) hand-edit `/etc/containerd/config.toml` or assume a generic `nvidia-ctk runtime configure --runtime=containerd` against a non-k3s containerd applies here (K3s manages its own containerd config file at `/var/lib/rancher/k3s/agent/etc/containerd/config.toml`). Confirm detection with `grep nvidia /var/lib/rancher/k3s/agent/etc/containerd/config.toml` after (re)starting k3s. Source: [K3s Advanced Options — NVIDIA Container Runtime](https://docs.k3s.io/advanced#nvidia-container-runtime).
4. Install the **NVIDIA device plugin for Kubernetes** DaemonSet, with its pod spec patched to include `runtimeClassName: nvidia` (K3s does not make `nvidia` the cluster-wide default runtime unless you explicitly set `--default-runtime`) — this is called out directly in the K3s docs linked above.
5. Connect the cluster to Azure Arc: `az extension add --name connectedk8s` then `az connectedk8s connect -n <name> -g <rg> -l <region>` (outbound HTTPS only — compatible with the VM's no-public-IP, NAT-gateway-outbound design).
6. To validate GPU scheduling, create a pod spec that requests `resources.limits: {"nvidia.com/gpu": 1}` and sets `runtimeClassName: nvidia`, running an image that executes `nvidia-smi` or a small CUDA sample; confirm the node reports `nvidia.com/gpu` as an allocatable resource (`kubectl describe node`) and that the pod's output shows the GPU. (No specific image tag is prescribed here — pick one from NVIDIA's current NGC catalog or your own base image at the time you run this, since previously-cited placeholder tags are not guaranteed to exist.)
7. Confirm the cluster shows as connected in the Azure portal. When finished, stop the Kubernetes GPU workloads before resuming Compose. If removing the experiment entirely, disconnect the Arc resource with `az connectedk8s delete -n <name> -g <rg>` while the cluster is reachable, then uninstall K3s. Uninstalling K3s is not required just to switch workloads.

This gives a real, working "Arc + GPU Kubernetes" connectivity/scheduling test — explicitly scoped as a self-managed cluster experiment, not a certified AKS-Arc deployment, since no Microsoft "AKS on X" product targets this VM or this GPU.

## Caveats and things that could not be confirmed

- **GPU Operator vs. existing host state**: [`bootstrap-host.sh`](../h100-spot-llm-lab/scripts/bootstrap-host.sh) already installs the NVIDIA datacenter driver and Container Toolkit, and registers it with **Docker only** (`nvidia-ctk runtime configure --runtime=docker`). If you instead choose the **NVIDIA GPU Operator** (rather than the manual device-plugin route above), the Operator already includes the device plugin as one of its managed components; do not separately install a second device plugin. For this host's pre-installed driver/toolkit, NVIDIA documents disabling Operator driver/toolkit management. `toolkit.enabled=false` only works if the node's container runtime (K3s's embedded containerd here) already has NVIDIA runtime support configured; Docker-only registration is not sufficient. See [NVIDIA's installation guide](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/getting-started.html) and [preinstalled-driver guidance](https://developer.nvidia.com/blog/adding-mig-preinstalled-drivers-and-more-to-nvidia-gpu-operator/).
- **Stop existing GPU consumers first**: the current VM only has 1–2 H100 GPUs ([`provision-spot-vm.sh`](../h100-spot-llm-lab/infra/provision-spot-vm.sh) — NC40 has one H100 NVL, NC80 has two). Running the Compose vLLM stack and a k3s GPU workload at the same time will contend for those GPUs. Stop whichever workload isn't under test; the Docker and K3s installations can coexist.
- **Nested virtualization on NC-series H100 VMs**: no Microsoft Learn page could be found that explicitly confirms (or denies) nested virtualization support on `Standard_NC40ads_H100_v5` / `Standard_NC80adis_H100_v5`. Generic nested-virtualization docs (Azure Lab Services, Hyper-V troubleshooting) describe the feature only in the context of specific Dv3/Ev3/Lab-Services templates, not GPU VM families, and do not address GPU passthrough into a nested guest at all. **Do not assume support** — this would need direct verification with Azure support/capacity docs or a support ticket before attempting it.
- **Azure Spot eviction**: Spot VMs have **no SLA** and can be evicted with **~30 seconds' notice** (Deallocate or Delete policy); evicted-Deallocate VMs keep their disks and can be restarted when capacity returns, but there's no guarantee of reallocation ([Azure Spot Virtual Machines](https://learn.microsoft.com/azure/virtual-machines/spot-vms)). The existing provisioner already uses `--priority Spot --eviction-policy Deallocate --max-price -1` ([`provision-spot-vm.sh`](../h100-spot-llm-lab/infra/provision-spot-vm.sh)). Any Arc-connected cluster on this VM will show as "Offline"/disconnected in Azure whenever the VM is evicted or stopped — expected and acceptable for an experiment, not for anything that needs continuous Arc connectivity.
- **Single-node limitation**: both supported VM sizes are single-VM (no multi-node HA); a k3s/kubeadm cluster here is inherently single-node, so this experiment validates connectivity/GPU-scheduling mechanics only, not HA or multi-node Arc Kubernetes behavior.
- **GPU Operator + Spot interaction is unresolved, and is an AKS-managed-cluster caveat, not a verified k3s one**: Microsoft's own AKS NVIDIA GPU Operator doc flags an *open* consideration for GPU Operator on Spot instances and links out to an NVIDIA GitHub issue rather than giving a resolution ([Use NVIDIA GPU Operator on AKS](https://learn.microsoft.com/azure/aks/nvidia-gpu-operator), "Note" under both tabs; [NVIDIA/gpu-operator#577](https://github.com/NVIDIA/gpu-operator/issues/577)). That caveat is documented specifically in the context of **AKS-managed node pools**, not k3s on a self-managed Spot VM — treat it as a signal that Spot+GPU-Operator interactions are generally under-documented, not as direct evidence about k3s behavior.
- **No single, official "AKS enabled by Azure Arc" product runs on a standalone Azure VM**: per the official platform comparison, all four "AKS Hybrid and Edge" variants (Azure/cloud AKS, AKS on Azure Local, AKS Edge Essentials, AKS on Windows Server) target either the Azure control plane itself or a specific on-premises/edge host type — none of them describe "run it inside a regular Azure IaaS VM" as a deployment target ([Compare AKS features across cloud, edge, and on-premises platforms](https://learn.microsoft.com/azure/aks-hybrid-edge/aks-platforms-compare)).
